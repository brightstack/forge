# Forge topology compared with Matt Pocock's current skills

Forge should adopt Pocock's progressive-disclosure and clarification mechanics, but keep its own accountable Wave and Review leads. Pocock's current corpus does not define the integrated multi-agent delivery topology Forge needs, and parts of it demonstrate the review recursion and artifact bloat Forge is designed to avoid.

## 1. What the compared system actually does

"Pocock's skills" is not one canonical SDLC. I inspected the promoted workflow in Matt Pocock's public `mattpocock/skills` repository at current `main`, commit [`6654f6b60cd9d5be8b54c6fafe44346dabeb3b76`](https://github.com/mattpocock/skills/commit/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76), plus Pocock's first-party AI Hero documentation. I excluded community issues and third-party extensions as authority.

The promoted [`ask-matt` main flow](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/engineering/ask-matt/SKILL.md) is conditional: [`grill-with-docs`](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/engineering/grill-with-docs/SKILL.md) aligns intent and records domain language; a high-fidelity question can detour through a prototype; small work goes directly to `implement`; multi-session work becomes `to-spec`, then tracer-bullet `to-tickets`, then one fresh `implement` session per ticket. `implement` runs TDD, checks, `code-review`, and commits. `wayfinder` is a slower decision-ticket map reserved for huge, foggy work.

Packaging is the central design. Skills are small, editable, composable folders. User-invoked transition skills cannot fire autonomously; model-invoked discipline can. `ask-matt` is the human-facing router. [`writing-for-agents`](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/productivity/writing-for-agents/SKILL.md) treats descriptions and AGENTS.md lines as context pointers: inline what every path needs, disclose branch-specific reference, keep one source of truth, and prune sprawl, sediment, duplication, and no-op instructions. Its [skill mechanics](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/productivity/writing-for-agents/SKILL-MECHANICS.md) explicitly use a router when humans can no longer remember the skill set.

Subagents have narrow uses: gather facts during [`grilling`](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/productivity/grilling/SKILL.md), run background research, resolve Wayfinder research tickets, or perform the two independent axes of [`code-review`](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/engineering/code-review/SKILL.md). The main implementation path uses separate human-invoked ticket sessions, not a canonical Lead -> Worker -> integration hierarchy.

## 2. Strong matches with Forge

- **Progressive disclosure:** Forge's one public skill with internal subskills can match Pocock's information hierarchy if each phase and persona is loaded only through precise route or task pointers. Forge's small kernel and minimal binding mechanics fit Pocock's single-source-of-truth rule.
- **Clarification before mutation:** Pocock separates facts the agent retrieves from decisions the human owns, asks dependent questions only when prerequisites settle, and requires shared understanding before action. Forge's Intake, authority-gap return, and conditional Research use the same boundary. Pocock's later warning about [over-grilling](https://www.aihero.dev/things-people-get-wrong-with-grill-me-and-grill-with-docs) supports Forge's materiality test rather than a universal interview.
- **Durable intent without repeated discovery:** [`to-spec`](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/engineering/to-spec/SKILL.md) synthesizes agreed conversation and explicitly forbids another interview. Forge similarly freezes a Spec bundle before Plan and Build.
- **Outcome slices and dependency fronts:** [`to-tickets`](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/engineering/to-tickets/SKILL.md) creates complete, verifiable vertical slices with blocking edges. This strongly matches Forge Issues, dependency-ready Waves, and coherent Worker outcomes.
- **Independent review dimensions:** Pocock separates Standards from Spec compliance in parallel contexts. Forge's read-only Judges generalize that sound idea to correctness, compliance, overengineering, and browser QA while retaining one accountable Reviewer.

## 3. Material differences or contradictions

- **Control model:** Pocock keeps major transitions user-invoked with `disable-model-invocation`; the human explicitly starts each ticket's build. Forge selects one route, then lets the assigned Lead advance work inside stable gates and the independent Reviewer decide each gate.
- **Lifecycle and artifacts:** Pocock skips a durable spec and tickets when work fits one context. Multi-session work has a spec and ticket approval, but no separate formal Plan artifact, Spec Review, or Planning Review. Forge's full Build route always has Spec and Plan phases with bundle-level reviews.
- **Build topology:** Pocock's default is one self-contained ticket per fresh session. His [phase-boundary guidance](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/skills/engineering/ask-matt/PHASE-BOUNDARIES.md) permits a tight AFK task to become a subagent, but does not establish a lead who dynamically partitions, integrates, and proves one Wave candidate. Forge does.
- **Review accountability:** Pocock's review skill aggregates two subagent reports side by side and explicitly refuses to merge or rerank them. Forge requires the Reviewer Lead to validate evidence, reconcile lenses, and own one verdict. Pocock's `implement` also calls review from the authoring session, while his current [code-review guide](https://www.aihero.dev/skills-code-review) prefers a fresh reviewer because same-context review carries the builder's assumptions.
- **Personas:** Pocock packages procedures and vocabulary, not BMAD-like persona agents. Forge's role identities and personality matrices are an independent bet. They conflict with Pocock's pruning rule if traits consume context without changing a reachable decision.

## 4. Failure modes Forge should avoid copying

- **Universal or unbounded grilling:** The [repository README](https://github.com/mattpocock/skills/blob/6654f6b60cd9d5be8b54c6fafe44346dabeb3b76/README.md) says to grill every change, while Pocock's later guidance says large or overlong grilling exhausts context and delays the prototype or code that would answer the question. Keep Forge clarification conditional on material ambiguity.
- **Artifact inflation:** The current `to-spec` template asks for a "LONG" and "extremely extensive" user-story list. That is directly at odds with Forge's simplicity rule when completeness can be expressed as concise ACs, terms, and constraints.
- **Recursive review fan-out:** Pocock's [first-party code-review page](https://www.aihero.dev/skills-code-review) documents a shipped failure in which review subagents rediscover `code-review` and create 50-plus agents. Forge's "Verify is not reviewed recursively" rule must be mechanical: Judges cannot spawn Judges or invoke Verify.
- **Review at every ticket:** Pocock's normal rhythm reviews each implemented ticket. Copying that into a Wave with Workers would multiply gates and encourage local optimization before integration. Forge's one frozen Wave candidate and one review boundary is the better fit for its topology.
- **Skill and persona sediment:** Pocock's own writing warns that more files and always-loaded descriptions spend both attention and human indexing cost. A single public Forge skill still bloats if it embeds every phase, persona matrix, template, and exception rather than pointing to them conditionally.

## 5. Concrete recommendations

- **Adopt:** Treat every Forge skill description, agent assignment, and artifact pointer as a trigger contract. Keep the always-loaded router to route names, gate semantics, and branching conditions.
- **Adapt:** Use Pocock's grilling mechanics inside Intake and authority-gap handling: retrieve facts, ask decision frontiers with recommendations, prototype high-fidelity unknowns, record the answer once, then stop interviewing.
- **Adopt:** Preserve tracer-bullet outcomes and real blocking edges. Size Issues by coherent behavior, contract, and proof, not by file count or a fixed token heuristic.
- **Adapt:** Keep independent Judge contexts, but make the Reviewer Lead validate and rank evidence into one verdict. Add an explicit no-recursion/no-delegation clause to every Judge base instruction.
- **Reject:** Do not import mandatory exhaustive user-story lists, review-per-Worker, or rich persona prose that cannot name a decision it changes.
- **Evaluate:** Run behavioral comparisons of (a) one fresh implement session per Issue versus a Wave Lead with bounded Workers, and (b) lean role instructions versus full persona matrices. Measure integration defects, reopened authority decisions, review precision, human turns, and total context load.

## 6. Source and evidence limitations

The repository is a fast-moving practitioner corpus, not a controlled evaluation. This review pins current `main` as inspected on 2026-08-30; the latest tagged release was [v1.2.3](https://github.com/mattpocock/skills/releases/tag/v1.2.3), while `main` contained later changes. Official sources contain live tensions: "grill every change" versus warnings against over-grilling, same-session review in `implement` versus fresh-session review guidance, and a known recursive-review bug not yet fixed in the shipped skill. Conclusions above concern observable workflow contracts, not proven productivity or quality gains.
