# Claude Code Ultracode, dynamic workflows, and agent teams: Forge comparative review

Pinned target: the supplied Forge brief plus `VNEXT-D1` through `VNEXT-D12` in the accepted-decision draft. The conclusion is that Forge's phase-internal topology is strongly compatible with Claude Code's ordinary subagents and parts of dynamic workflows, but it should not be remodeled as an agent team. Dynamic workflow machinery should remain a host runtime beneath Forge's stable phase, authority, candidate, and review contracts.

## 1. What the compared system actually does

| Mechanism | Documented behavior |
|---|---|
| **Ultracode** | A Claude Code setting, not another model tier. It combines `xhigh` reasoning effort with automatic workflow orchestration. Claude decides whether each substantive request warrants a workflow, and one request may become successive workflows for understanding, changing, and verifying. A typed `ultracode` keyword instead opts one prompt into workflow generation without changing session effort. ([workflow docs](https://code.claude.com/docs/en/workflows)) |
| **Dynamic workflow** | Claude writes a task-specific JavaScript orchestration script. An isolated runtime executes `agent()`, `parallel()`, `pipeline()`, and phase logic while intermediate values stay outside the main conversation; the run returns one result. Scripts can fan out, synthesize at a barrier, adversarially verify, filter, run tournaments, or loop to a stop condition. They can select models and per-agent worktree isolation. Runs are inspectable and resumable within the session; the generated script is stored under the session directory and can optionally be saved for reuse. There is no mid-run user input. Current limits include 16 concurrent and 1,000 total agents per run; the default size guideline aims below 15 agents but is advice, not a cap. ([workflow docs](https://code.claude.com/docs/en/workflows), [Anthropic workflow patterns](https://claude.com/blog/a-harness-for-every-task-dynamic-workflows-in-claude-code)) |
| **Ordinary subagent** | A delegated worker inside one Claude Code session with a fresh context, its own prompt, model, tools, and permissions. It returns a result to its caller and normally runs in the background. Current Claude Code allows nested subagents up to three layers by default and 20 concurrent ordinary subagents; Ultracode sessions are exempt from that ordinary concurrency limit. ([subagent docs](https://code.claude.com/docs/en/sub-agents)) |
| **Agent team** | A separate, experimental feature: one fixed lead plus full independent Claude Code sessions, direct peer messaging, and an optional shared dependency-aware task list whose work can be assigned or self-claimed. Teammates share the working directory rather than receiving automatic worktree isolation, and the user can talk to each teammate. Teams are disabled by default and have documented resumption, task-status, shutdown, nesting, and permission limitations. ([agent-team docs](https://code.claude.com/docs/en/agent-teams)) |

Thus, “Ultracode,” “dynamic workflow,” “subagent,” and “agent team” are not synonyms. Dynamic workflows orchestrate subagents through generated code; agent teams coordinate independent sessions through shared mutable state and messages.

## 2. Strong matches with Forge

- **Dynamic inside, stable outside.** A generated workflow sizes and shapes its graph for the specific task, while Forge fixes the lifecycle and phase contract. This closely matches Forge's dynamic, ephemeral within-phase graph beneath a stable SDLC.
- **Lead-and-synthesize topology.** Workflow fan-out returns through a synthesize barrier to one result. Ordinary subagents return to their caller. Both support Forge's Builder ownership of the sole integrated candidate and Reviewer ownership of one verdict.
- **Independent evidence.** Dynamic workflows explicitly support adversarial verification and competing hypotheses. This supports read-only Judges working from a frozen candidate, provided their reports remain evidence to the Reviewer rather than independent verdicts.
- **Outcome-sized delegation.** Anthropic recommends independent work with clear deliverables and warns that coordination overhead dominates tiny tasks. That agrees with Forge's meaningful Worker outcomes and stable interface boundaries.
- **Proportional runtime choices.** Workflow scripts can route model strength and worktree isolation per stage. That fits Forge's semantic model tiers and optional short-lived worktrees without making either part of the durable artifact model.
- **Context isolation.** Focused subagent contexts reduce goal drift and keep verbose exploration out of the lead context. This fits lean Worker/Judge bots that receive only task, authority, scope, tools, and proof.

## 3. Material differences or contradictions

1. **Workflow scripts are inspectable runtime records; Forge's graph is not a product artifact.** Claude Code always writes the generated script under session state and allows saving it. Forge should treat that as host-owned runtime state, not add workflow scripts, staffing plans, transcripts, or task manifests to its canonical artifacts.
2. **Anthropic often verifies each fanned-out unit.** Its examples use a verifier per finding or file, sometimes two reviewers per file. Forge deliberately reviews one integrated phase candidate, never each Worker or Issue. Worker self-tests and integration checks are compatible; per-contributor gates and verdicts are not.
3. **Ultracode may autonomously chain “understand/change/verify” workflows.** Forge has accepted phase order, exclusive artifact ownership, and explicit gates. Generated workflow phases cannot replace Spec, Plan, Build, Verify, or Simplify, nor allow a Builder-run verifier to publish the Review verdict.
4. **Agent teams distribute coordination.** Peer messaging, self-claiming tasks, task locks, and direct user steering weaken Forge's single accountable Lead and create exactly the durable staffing/task machinery `VNEXT-D3/D4/D6` exclude. Agent teams also do not isolate teammate edits by default; Anthropic warns that same-file edits overwrite each other.
5. **Workflows cannot ask the user mid-run.** Forge requires an unsupported material decision to return `AUTHORITY_GAP(owner, obligation)`. A workflow must surface that gap to its Lead and stop; it cannot infer intent merely to keep the run moving.
6. **Ultracode is host-specific.** Encoding it as Forge's `deep` model tier would conflate reasoning strength with an orchestration policy and violate Forge's provider-neutral semantic mapping.

## 4. Failure modes Forge should avoid copying

- **Agent-count theater and cost blowups.** Anthropic warns workflows use meaningfully more tokens; its earlier production research observed multi-agent research using about 15 times chat tokens and found poor fit where dependencies dominate. The figure is research-domain evidence, not a coding benchmark, but it reinforces eligibility based on real parallelism rather than task size alone. ([multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system))
- **False confidence from local green checks.** Anthropic's compiler experiment needed unusually strong tests, still suffered regressions, and cautioned that passing tests do not establish shipping quality. Forge's integrated candidate, complete obligation check, and independent Review must remain authoritative. ([C-compiler experiment](https://www.anthropic.com/engineering/building-c-compiler))
- **Coordination state becoming architecture.** Agent-team task lists can lag and block dependencies; teammates can overwrite files; in-process teammates do not resume. Copying these mechanics would add failure-prone state without improving Forge's artifact contract.
- **Verification explosion.** Verifier-per-item patterns multiply cost and can make many shallow checks look stronger than one reconciled boundary review. Judges should be chosen by material quality dimension, not contributor count.
- **Authority bypass through autonomy.** Ultracode skips the workflow-plan prompt in auto mode, and workflows accept no mid-run user input. Forge must not let a host convenience bypass route choice, accepted intent, one-way-door authority, or external-action authorization.
- **Lossy handoffs.** Fresh subagents do not inherit lead conversation history. Pointer-only assignments need exact accepted authority and interface context; a Lead-authored summary alone is not a safe substitute.

## 5. Concrete recommendations

- **Adopt:** ordinary subagent semantics for Workers and Judges: fresh bounded context, least tools, explicit model tier, exact authority pointers, clear deliverable/evidence, and return to one accountable caller.
- **Adopt:** dynamic fan-out, synthesis barriers, competing hypotheses, model routing, optional worktree isolation, and runtime progress visibility inside a phase when independence is demonstrated.
- **Adapt:** use generated workflow scripts only as ephemeral host execution plans beneath the active Phase Lead. A resumed run must revalidate that its accepted inputs and candidate still apply; its saved runtime results never become Forge acceptance evidence by themselves.
- **Adapt:** allow Worker self-tests and Builder integration checks, but move formal adversarial Judges to the frozen integrated candidate and keep one Reviewer verdict.
- **Reject:** agent-team shared task lists, self-claiming, peer-to-peer coordination, per-task locks, and teammate directories as Forge's default topology. Also reject `ultracode` as a generic model tier or lifecycle route.
- **Reject:** automatic continuation across an authority gap and any per-contributor review gate.
- **Evaluate:** compare three host executions on the same accepted Waves: Lead plus ordinary subagents, a phase-scoped dynamic workflow, and an agent team. Measure obligation coverage, introduced defects, unowned decisions, integration conflicts, token/elapsed cost, and Review findings. Promote a mechanism only where it beats the simpler control on behavioral evidence.

## 6. Source and evidence limitations

This review uses current official Anthropic/Claude documentation and official Anthropic engineering/blog posts, checked 2026-08-30. Dynamic workflows are now documented as generally available, while agent teams remain experimental and their mechanics have changed across recent Claude Code versions. Claude Code's implementation is not established here from inspectable source; statements about Ultracode and workflow internals therefore rely on official product documentation. Anthropic's workflow examples are usage guidance, not independent comparative evaluations. The multi-agent research and compiler results demonstrate possible behavior at high scale but do not prove that the same cost/performance profile applies to Forge's smaller delivery phases. Recommendations that go beyond explicit documentation are identified above as Forge-specific design judgments.
